## 1. 项目定位与最终愿景

WearMate 是一个以「我的形象 + 我的衣橱 + 智能搭配」为核心的 AI 穿搭应用。最终体验为：

1. 用户上传本人全身照，生成**一眼能认出是本人**、适合展示服装的 2D 轻写实卡通分身。
2. 用户上传淘宝等电商平台的服装截图，或自己拍摄的衣服照片，AI 识别衣物并整理为个人数字衣橱。
3. 系统结合天气及可选场景，从**用户实际拥有的衣服**中推荐至少两套风格不同的穿搭。
4. 用户在自己的 2D 分身上切换、查看和调整穿搭，能够保存喜欢的方案。

**核心价值：不是生成陌生模特的穿搭图，也不是只提供文字建议，而是让用户用自己的衣服，为像自己的 2D 分身进行可视化搭配。**

### 已确定的产品原则

- **坚持 2D，不做 3D**，不使用 Three.js/3D 虚拟试衣。
- 不做大头 Q 版、儿童换装游戏；选择**正常人体比例、精致轻写实的 2D 插画**。
- 本人相似度的合理目标是：**「一眼能看出是这个人，并且适合做穿搭展示」**，不追求真人级精确复刻。
- **设计和美术品质与功能正确性同等重要**；不是做一个凑齐功能的廉价 Demo。
- 页面视觉方案尚未最终确定，必须预留大幅修改空间。
- 阶段式交付：每阶段实现、运行、验收通过后再继续，不为堆功能牺牲质量。

## 3. 阶段 0：本次任务范围

**阶段 0 目标：开发一个可以直接运行、视觉高质量、交互真实的「2D 时尚换装工作台」。**

必须交付：

- 一个整体设计精致、有品牌感的 Web 界面；
- 一个正常人体比例、画风统一的高质量 2D 示例角色；
- **人物与服装分层**的换装系统；
- 至少 **2 件上衣、2 条裤子、2 双鞋**，可分别切换；
- 至少 **2 套完整且有明显风格差别的预设搭配**：舒适休闲、精致通勤；
- 衣物选择、当前选中状态、方案 A/B 切换等真实交互；
- 清晰、模块化的工程结构，方便后续加照片生成、衣橱和推荐功能；
- 桌面端与移动端的合理适配，以及实际运行/基本验收。

### 本阶段严格不做

- 用户照片上传、AI 人像生成；
- 淘宝截图识别、AI 衣物识别、真实衣服自动转换；
- 天气 API、智能推荐算法；
- 用户账号、后端数据库、电商、社交；
- 3D、360° 旋转试衣、AR、桌宠动画。

不得把未实现的模块包装成已可用的功能。可以保留未来入口，但要标记「即将推出」或保持非交互，不设置看似可点击但无反应的按钮。

## 4. 视觉与产品美术标准（硬性要求）

### 4.1 视觉定位

目标气质：**现代时尚品牌官网 × 精品数字衣橱 × 时尚杂志编辑排版**。

关键词：高级、克制、有审美、现代、精致、富有画面感、有辨识度、轻盈但不幼稚。

**视觉灵感图仅作为方向探索，不是不可修改的最终 UI 稿。**不要求完全照搬图中的布局、配色、人物或模块。

设计要求：

1. **人物是第一视觉焦点**，全身形象应有足够展示面积，不能缩在小卡片里。
2. 优先考虑有主次的构图、较大展示舞台、编辑式排版、舒服的留白与精细字级。
3. 页面应有统一的字体、色彩、材质、图片处理与控件体系，不依赖杂乱装饰营造「高级」。
4. 桌面端可以采用不对称布局，移动端需要重新组织信息层级，不能简单等比压缩。
5. 衣物选择卡片、方案切换、hover/selected、轻量过渡动画均需清晰和精致。
6. 配色方案目前是**可修改设计决策**，不要将某套米白色/绿色固定成不可变风格。
7. 如果无法拿到足够优秀的素材，应诚实指出缺口并保留良好的架构，**不要用粗糙占位图冒充成品**。

### 4.2 明确避免

- 千篇一律的 SaaS 后台、白色卡片堆砌、毫无层次的仪表盘；
- 儿童游戏风格、Q 版大头娃娃、火柴人、粗糙多边形/几何 SVG 人物；
- 不同来源、透视和光影互相冲突的拼贴素材；
- 过多渐变、发光、阴影、装饰性元素；
- 人物被 UI 挤得过小、上下被裁切、服装主体显示不全；
- 大量无响应按钮与「做了但不能用」的假交互。

### 4.3 人物与服装美术

- 示例人物为**成年人正常人体比例的 2D 轻写实插画**，大致 7–7.5 头身，可依据实际审美优化。
- 固定正面或近正面站姿，完整展示头到脚；身体与衣服保持统一姿态与视角。
- 精致的发型/五官、合理的身体轮廓、统一的线稿、阴影和用色。
- 不采用完整人物图片整张替换来「假装换装」；**切换衣物时相同人物的脸、发型、身体、姿态与比例必须保持稳定**。
- 素材尽量透明背景并具有明确的图层结构。各服装版型应与同一套人体锚点对应。
- 不使用随机的独立服装商品图直接覆盖人物，导致袖口、领口、腰线、腿部错位。

> **现实约束：**AI 编码模型能实现 UI 和渲染逻辑，但不必然能制作出高质量、可分层且彼此对齐的角色美术。若条件不足，应先构建正确的分层协议、使用风格统一的合规示例素材并说明限制，不得宣称已解决任意真实衣物换装。

## 5. 交互与页面组成

围绕**一个高保真穿搭工作台**组织 UI，允许合理调整布局，须具备以下能力：

### 5.1 人物展示区

- 页面主视觉：大幅全身角色；
- 有设计感而不抢戏的展示背景；
- 角色完整可见，不遮挡重要部位；
- 换装后立即同步画布，可有细腻的淡入淡出动效。

### 5.2 衣物选择区

- 上衣、裤子、鞋子三个分类；
- 每类至少 2 款衣服及清晰可辨的缩略图；
- 点击后真实改变角色上的对应图层；
- 清楚标出当前选中服装。

### 5.3 预设方案区

- 方案 A：舒适休闲；
- 方案 B：精致通勤；
- 点击方案 A/B，一次性切换所有对应服装；
- 显示当前方案或当前组合的信息。

### 5.4 品牌与导航

- 以 **WearMate** 作为暂定品牌名；
- 导航清楚、不喧宾夺主；
- 为未来的「我的衣橱」「我的形象」「智能推荐」预留信息架构，而非提前假实现这些功能。

## 6. 2D 换装系统：关键技术要求

### 6.1 渲染方式

建议技术栈：

- React + TypeScript + Vite；
- CSS/Tailwind CSS（按工程实际选择）；
- SVG 分层渲染或 Canvas 2D / react-konva（根据素材形式选择，**说明选择理由**）。

**不要使用 3D / Three.js。**

### 6.2 角色与衣物图层

角色应具备明确的可配置结构，示意：

1. 背景；
2. 身体基础层；
3. 鞋子；
4. 下装；
5. 上衣；
6. 外套（可仅预留接口）；
7. 头部与头发、前景手臂/遮挡层（按实际遮挡关系细分）。

图层顺序以视觉正确为准，不能把这份示意顺序机械写死。角色配置与衣物素材应包含统一的坐标系、基准尺寸、位置/缩放、锚点、遮挡层级等必要信息。

### 6.3 换装行为

- 各类衣物**独立可替换**，互不影响；
- 同一套角色身体与头脸持续复用，不因衣物切换重新生成整个人物；
- 预设方案使用服装 ID 组合，而不是多张事先渲染好的「整身人物」图片；
- 切换方案和手动选衣保持状态一致；
- 不应出现明显错位、穿模、裁切、闪烁、缺层；
- 服装的显示位置在不同窗口尺寸下仍保持与角色的相对对齐。

## 7. 架构：把「地基」和「视觉外观」分开

### 7.1 三层解耦

**视觉设计层**：主题变量、字体、颜色、间距、排版、导航、动效、衣物面板。应能单独改造。

**人物换装层**：角色配置、素材注册、统一画布坐标、图层合成、锚点、当前衣物组合。作为独立组件/模块实现。

**业务与数据层**：示例衣物数据、服装分类、预设穿搭、选择状态。后续可以接入数字衣橱与推荐系统。

### 7.2 可替换设计的具体要求

- 颜色、字体、间距、圆角、阴影等通过主题 token / CSS 变量集中管理，避免组件内到处硬编码；
- 页面布局与换装渲染器分离：将来更换整体 UI，不需重写换装逻辑；
- 角色与衣服素材独立于页面组件管理，不能直接耦合到某张大背景图；
- 人物比例、素材画布、服装锚点必须有文档说明；
- **更换页面 UI 相对容易，但更换人物的身体比例/画风可能需要重新制作衣物素材**，不可承诺无成本任意替换；
- 避免单文件巨大组件、过度抽象、提前接入不必要的后端与依赖。

### 7.3 数据结构建议

至少将以下概念分离：

- `AvatarConfig`：角色 ID、基础素材、画布坐标规格、图层配置；
- `Garment`：服装 ID、类别、名称、缩略图、换装素材、锚点/位置/层级等；
- `Outfit`：方案 ID、名称、各类别服装 ID；
- `WardrobeState` / `OutfitSelection`：当前选中服装组合与状态。

命名和具体接口可以按工程合理调整，但要保持可替换性。

## 8. 开发执行流程（直接实施，不需要逐步等待确认）

1. 先检查本地工程和可用依赖，形成**简短**的技术与设计方案。
2. 确定示例人物及衣服素材的获取/制作方案；验证能否满足**统一角色、统一坐标、独立图层**，不要只找到好看的整身图就当换装成功。
3. 建立前端项目骨架、统一设计 token 和基本组件。
4. 实现独立的 2D 角色渲染与服装图层切换。
5. 接入 2 套预设穿搭与逐件换装交互。
6. 制作高保真的桌面工作台，并适配移动端。
7. 本地运行、检查浏览器错误、功能与布局；有浏览器预览/截图能力时检查实际界面，并根据视觉问题调整。
8. 对明显的人物失真、衣物错位、过小展示、元素拥挤与风格不统一问题继续打磨，**不要仅以构建成功作为完成标准**。
9. 汇报已完成、未完成、受资源限制的部分及后续扩展接口，保留实际可运行的成果。

对素材能力如有局限，请明确告知：哪些是真实可换装素材、哪些是演示替代或占位。不得用改变整张人物照片代替图层换装而宣称完成。
